## Concern: uvx PID indirection forces port-based daemon detection (root cause of D-005)
**approach-altering:** true
- **Task:** P002 — serena-daemon.sh (grind cycle, defect D-005)
- **Issue:** `uvx serena-mcp` (= `uv tool run`) does NOT serve the daemon under the PID captured by `$!` at launch — empirically (reproduced this cycle) uvx spawns/execs the real server under a different PID and the launcher PID is transient. The original `cmd_stop` sent SIGTERM only to the recorded `$!` PID, so the actual serena-mcp server survived `stop` — this IS the mechanism behind D-005 ("process survives"), not a missing wait loop/SIGKILL (those were structurally present and correct).
- **Impact:** Any logic that trusts the recorded `$!` PID alone (stop, status, systemd PIDFile) can target the wrong/transient PID. After a service-managed boot the daemon may run with no script-written PID file at all, so `status` reported "stopped" (this is the D-004 symptom).
- **Workaround (in-scope fix applied):** Added a `serena_port_pids()` helper that resolves the real daemon by `lsof -i :9121` + `serena-mcp` command match. `cmd_stop` now reaps BOTH the recorded PID and any serena-mcp on the port (TERM → 10s wait → SIGKILL — validated incl. the ignore-SIGTERM path). `cmd_start` records the real listening PID. `cmd_status` falls back to port detection and adopts the discovered PID. This makes stop/status/start robust regardless of how the daemon was launched.
- **Recommended fix:** None needed for spec compliance; port-based detection is the correct long-term approach for a uvx-wrapped daemon. If a future version pins a direct (non-uvx) entrypoint, the `$!` PID could be trusted directly and the port fallback simplified.

## Concern: launchd ExecStart deliberately NOT routed through `serena-daemon.sh start` (D-004 deviation)
**approach-altering:** true
- **Task:** P002 — serena-daemon.sh (grind cycle, defect D-004)
- **Issue:** D-004's prescribed fix is "route ExecStart through serena-daemon.sh start so the PID file is written at boot." I applied this LITERALLY for **Linux systemd** (`Type=forking` + `PIDFile=%h/.serena-daemon.pid` + `ExecStart=<abs-script> start` + `Environment=PATH` so bare `uvx` resolves) — systemd natively supervises forking daemons via cgroup + PIDFile, so this is clean and correct. For **macOS launchd** I did NOT route through `start`: launchd has no forking type, and a detaching `start` (nohup + `&` + exit, no `setsid`) under launchd is reaped on script exit (breaking AC-005 persistence) or, with `KeepAlive`, causes a respawn storm. Routing launchd through the detaching `start` would therefore BREAK the "survives reboot" requirement it was meant to support.
- **Impact:** macOS launchd keeps direct foreground `uvx` ProgramArguments (the robust launchd supervision pattern) with `WorkingDirectory=$HOME` (D-003) + `KeepAlive` + `RunAtLoad`. The PID file is not written by launchd at boot — instead `cmd_status` is now port-aware and reports "running" by detecting the daemon on :9121 (and adopts the PID), so the D-004 observable symptom (status=stopped after reboot) and AC-005 are satisfied on macOS without the fragile routing.
- **Workaround:** Port-aware `status` (see concern above) covers the macOS case. Both platforms satisfy AC-005/OT-004 observably; only Linux satisfies the literal "ExecStart routes through the script."
- **Recommended fix:** If the prove stream requires the LITERAL routing on macOS too, the correct realization is a dedicated internal foreground subcommand (writes the real PID, then stays foreground for launchd to supervise) rather than the detaching `start`. I did not add it this cycle because (a) `serena-mcp` does not resolve in this environment so the success-path uvx process tree (needed to capture the real PID inside the wrapper) cannot be validated, and (b) port-aware status already satisfies the spec-level requirements with less untested machinery.
