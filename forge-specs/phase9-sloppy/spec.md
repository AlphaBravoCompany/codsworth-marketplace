## User Stories

> **Every US and every AC carries citations.** The `As a / I want / so that` narrative is Claude's synthesis of the user's answers; the citation proves the synthesis is grounded.

### US-001: Auditable envelope acknowledgement [derived from A-001, A-002, A-005]
**As a** downstream auditor, **I want** every envelope's acknowledgement (or rejection reason) recorded durably, **so that** I can trace any envelope's fate to a specific decision point.

**Source answers:**
- A-001: "the persistence layer is not allowed to leak into `src/handlers/`"
- A-002: "single entry point is the function `process_envelope(envelope, mode)`"
- A-005: "audit-traceable rejection path — silent drops are not acceptable"

#### AC-001-01: Acknowledgement record includes the state transition trail [from A-003]
Given a successfully processed envelope, when the acknowledgement record is read, then the record carries the RECEIVED→VALIDATED→ACKNOWLEDGED transition trail inline.

#### AC-001-02: Rejection record names the violated bound [from A-005]
Given an envelope whose payload exceeds the configured cap, when the processor rejects the envelope, then the rejection record's `reason` field names the bound that was violated.

### US-002: Mode-driven response shape [derived from A-002, A-004]
**As a** consumer of the acknowledgement endpoint, **I want** the response shape to depend on the requested mode, **so that** "fast" callers can skip the integrity-chain payload that "thorough" callers need.

**Source answers:**
- A-002: "a `mode` field that takes one of two string values, `\"fast\"` or `\"thorough\"`"
- A-004: "`mode=\"fast\"` MUST NOT carry a `verification_chain` in the response, and calls with `mode=\"thorough\"` MUST carry a non-empty `verification_chain` in the response"

#### AC-002-01: Fast mode omits verification_chain [from A-004]
Given a `process_envelope(env, mode="fast")` call, when the call returns successfully, then the response object MUST NOT contain a `verification_chain` field.

#### AC-002-02: Thorough mode includes non-empty verification_chain [from A-004]
Given a `process_envelope(env, mode="thorough")` call, when the call returns successfully, then the response object MUST contain a `verification_chain` field whose value is a non-empty array of strings.

### US-003: Backpressure-driven load shedding [derived from A-008]
**As a** pod operator, **I want** the processor to shed load when sustained ingest exceeds the safe threshold, **so that** downstream persistence does not collapse under burst pressure.

**Source answers:**
- A-008: "When sustained ingest exceeds 80 envelopes/second per pod for more than 30 seconds, the processor must shed load"

#### AC-003-01: Shedding emits retry_after_seconds [from A-008]
Given sustained ingest above the threshold, when the processor sheds load, then each early-rejection response includes a `retry_after_seconds` hint.

## Functional Requirements

- **FR-001**: The processor exposes `process_envelope(envelope, mode)` from `src/services/ack/processor.py` and nowhere else. [from A-002]
- **FR-002**: The processor enforces a configured payload-size cap; envelopes whose `x` exceeds the cap are rejected before the durable write step. [from A-005, A-006]
- **FR-003**: The acknowledgement record encodes the inline transition trail RECEIVED→VALIDATED→ACKNOWLEDGED. [from A-003]
- **FR-004**: The response shape branches on `mode`: `"fast"` omits `verification_chain`, `"thorough"` includes a non-empty `verification_chain`. [from A-004]
- **FR-005**: Sustained ingest above the configured threshold triggers load shedding with a `retry_after_seconds` hint per rejected envelope. [from A-008]
- **FR-006**: All evidence files committed during integration testing must reside on the same branch as the casting commit. [from A-007]

## Technical Design

The processor is implemented as a single async coroutine `process_envelope` exposed from `src/services/ack/processor.py`. The persistence layer uses an internal helper `_write_ack_record` that is private to `src/services/ack/`. HTTP handlers in `src/handlers/` invoke `process_envelope` exclusively; no handler imports the persistence helper directly.

The mode branch is a runtime conditional inside `process_envelope`; both branches share the same construction prefix and diverge only in whether `verification_chain` is computed and attached.

[Research finding from R1.5] [from reality.md Research Findings] Production runtime is Python 3.11.7 under uvicorn (one worker per pod), per the survey-extracted [IMPLICIT_FACT:RUNTIME] entry A-AUTO-002.
